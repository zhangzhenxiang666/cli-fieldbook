**适用场景：** 把项目依赖锁定为可复现的精确集合，导出给其他工具或部署流程使用，并在 CI 中强制"lockfile 必须与 `pyproject.toml` 一致"。

## 前提

- 工作目录位于项目内（当前目录或任一父目录有 `pyproject.toml`），否则这些命令报错退出。
- `uv.lock` 应提交版本控制；下文的 `<package>` 表示任意包名。

## 步骤

### 1. 加锁与升级

```sh
uv lock
uv lock --upgrade
uv lock --upgrade-package <package>
uv lock --upgrade-package <package>==<version>
```

[uv lock](cli:command:lock) 在 `uv.lock` 不存在时创建它；已存在时，旧内容作为解析偏好被沿用——依赖声明没有变化时再次加锁无效果，除非 `--upgrade`。升级始终受项目约束限制（声明了上界就不会越过）。重要边界：**上游发布新版本不会让 lockfile 过期**，升级必须显式触发。

### 2. 校验：--locked 与 --frozen

```sh
uv lock --check
uv sync --locked
uv sync --frozen
```

三者语义不同，不要混用：

- `uv lock --check`：断言 lockfile 最新，缺失或需更新即报错；与其他命令上的 `--locked` 等价。
- `--locked`（可用于 `uv sync`、`uv run`、`uv export` 等）：先校验 lockfile 是否最新，不新鲜即报错，不会顺手改写。
- `--frozen`：完全不检查新鲜度，直接以 lockfile 为准；lockfile 缺失报错，`pyproject.toml` 中尚未进入 lockfile 的依赖改动不会出现在环境里。

### 3. 导出

```sh
uv export -o requirements.txt
uv export --format pylock.toml -o pylock.toml
uv export --frozen --no-hashes -o requirements.txt
```

[uv export](cli:command:export) 支持 `requirements.txt`（默认）、`pylock.toml`（PEP 751）与 CycloneDX v1.5 JSON；给了 `-o` 时输出格式可从扩展名推断。导出前默认会重新加锁，CI 中通常加 `--frozen` 跳过。默认输出包含各依赖的哈希，目标工具不支持时用 `--no-hashes` 省略。workspace 默认导出根成员，`--package <package>` 选择具体成员。

### 4. CI 中的用法

```sh
uv lock --check        # 门禁：lockfile 过期即失败
uv sync --locked       # 安装并强制与 lockfile 一致
uv export --frozen -o requirements.txt --no-hashes
```

有依据的失败恢复：CI 中 `--locked` 失败说明 `pyproject.toml` 与 `uv.lock` 脱节。正确做法是在本地运行 `uv lock`、审阅差异并提交新 lockfile；不要在 CI 里删掉 `uv.lock` 重建（那会把未审阅的依赖变化直接发布出去），也不要改用 `--frozen` 掩盖不一致。

**执行结果与完成判断：** `uv lock --check` 与 `uv sync --locked` 退出码 0 分别代表"lockfile 新鲜"与"环境与 lockfile 精确同步"；导出文件存在且被下游工具接受（如 `pip` 能读取）才算导出完成。

**风险与边界：** `uv.lock` 是 uv 专用格式，其他工具需要 `requirements.txt`／`pylock.toml` 导出品。`--frozen` 跳过新鲜度检查，适合"信任 lockfile"的场景（如缓存加速），不能替代 `--locked` 的一致性门禁。

**未实测声明：** 本工作流依据 uv 0.12.22 固定提交的源码与官方文档快照编写，命令组合未在真实环境实测；`<package>`、`<version>` 为占位符。
