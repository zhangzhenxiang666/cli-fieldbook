**适用场景：** 用 `cargo doc` 生成并浏览 API 文档（含控制是否文档化依赖与私有项），用 `--message-format json` 把构建诊断交给工具消费并以 `build-finished` 判定消息流结束，以及在 CI 中用 `--locked`/`--frozen` 保证构建可复现。

## 前提

- 工作目录在包或工作区内；文档注释（`///`）与 doctest 的写法属于 rustdoc 范畴，本页只覆盖 cargo 侧命令。
- 打开浏览器依赖 `BROWSER` 环境变量或 `doc.browser` 配置（见[环境变量](../reference/environment.md)）。
- JSON 消息的字段与稳定性约定见[输出与消息格式](../reference/formatting.md)。

## 步骤

### 1. 生成并打开文档

```sh
cargo doc --open
```

完成前的状态行形态（说明性示例，`Generated` 后跟入口文件路径，依据 `cargo_doc.rs`）：

```console
 Generated /path/to/hello_world/target/doc/hello_world/index.html
```

[cargo doc](cli:command:doc)（别名 `d`）为本包与全部依赖生成文档，输出在 `target/doc`；`--open` 在生成结束后自动打开浏览器，入口是 `target/doc/<crate>/index.html`。再次运行时增量生成，已存在的文档文件会跨次保留；要清空重新生成，用 [`cargo clean --doc`](cli:command:clean)（man 手册注明文档生成是累积的）。完成信号：`Generated` 状态行（含入口文件路径）与退出码 `0`。`cargo doc` 自身也接受 `--message-format`，rustdoc 的诊断可同样进入 JSON 流。

### 2. 控制文档范围

```sh
# 说明性示例：只文档化工作区成员；包含私有项
cargo doc --no-deps --open
cargo doc --document-private-items
```

- `--no-deps` 跳过依赖的文档，只构建工作区成员的文档，常用在快速预览自己的 API 与 CI 中的内部文档检查。
- `--document-private-items` 把私有项也纳入文档，适合内部审阅。
- `--open`、`--no-deps`、`--document-private-items` 可以组合；`--output-format json` 存在于本版选项表但需要 nightly 的 `-Z unstable-options`，本工作流不依赖它。

### 3. 把诊断交给工具消费

```sh
# 说明性示例：构建并以 JSON 消息流交给下游工具
cargo build --message-format json
```

[cargo build](cli:command:build)（别名 `b`）加 `--message-format json` 后，cargo 把编译器诊断、生成的产物与构建脚本结果以"每行一个 JSON 对象"写入标准输出，`reason` 字段区分消息种类：`compiler-message`（诊断）、`compiler-artifact`（产物与文件名）、`build-script-executed`（构建脚本输出）、`build-finished`。流结束的标志是最后一条消息（说明性示例，字段见书《External tools》）：

```json
{"reason":"build-finished","success":true}
```

约定：

- `build-finished` 携带 `success` 布尔值且总是整条流的最后一条 cargo 消息——下游读到它即可停止解析；此后的输出（如 `cargo run` 启动的程序自身输出）不再是 cargo 的 JSON（书《External tools》）。
- `package_id` 字段是包的唯一标识，可直接作为多个命令的 `--package` 参数值（语法见工作流 08 的 pkgid）。
- JSON 只约束 cargo 与 rustc 的输出；过程宏或被运行程序的任意输出不受控，书建议的变通是只把以 `{` 开头的行当作 JSON 解析。
- 用途：诊断收集器、增量构建包装器、语言服务。格式细则与修饰符（`json-render-diagnostics` 等）见[输出与消息格式](../reference/formatting.md)。

### 4. CI 中的可复现构建

```sh
# 说明性示例：CI 流水线内的三个检查点
cargo fetch --locked
cargo build --locked
cargo test --frozen
```

- `--locked` 断言 `Cargo.lock` 在整个命令过程中不变：锁文件缺失或需要变更（例如清单改过而锁文件没跟上）时报错退出，而不是静默更新。CI 借此保证使用提交在仓库里的精确依赖版本。
- `--offline` 禁止一切网络访问；`--frozen` 等价于同时给出 `--locked` 与 `--offline`（源码 `cli.rs` 的帮助文本）。
- 两者都是全局选项，可与任意子命令组合；典型组合是先 `fetch` 预取，再以 `--frozen` 执行构建与测试，网络故障或版本漂移都会以非零退出码暴露（见[退出代码](../reference/exit-codes.md)）。

**状态变化一览：**

| 命令 | target/doc | target/debug | Cargo.lock | 网络 |
| --- | --- | --- | --- | --- |
| `cargo doc [--open]` | 写入 HTML | 不修改 | 首次生成 | 缺依赖时访问 |
| `cargo doc --no-deps` | 仅工作区成员 | 不修改 | 首次生成 | 缺依赖时访问 |
| `cargo build --message-format json` | 不修改 | 写入产物 | 首次生成 | 缺依赖时访问 |
| `cargo build --locked` / `--frozen` | 不修改 | 写入产物 | 断言不变 | `--frozen` 禁止 |

**风险与边界：** `cargo doc` 默认连依赖一起文档化，大型依赖树的文档构建耗时可观，CI 中建议 `--no-deps`。累积生成意味着改名或删除的条目可能残留旧页面，发布前的文档应从干净 target 目录生成。JSON 消息格式按"同 `--format-version` 内新增字段不算破坏"的策略演进（metadata 同理），消费端应容忍未知字段。`--locked` 失败说明锁文件与清单不一致，修复方式是本地正常构建后把更新过的 `Cargo.lock` 一并提交，而不是在 CI 里去掉该选项。
