**适用场景：** 为 IDE、编辑器插件与脚本提供机器可读的 cargo 视图：定位清单、读取工作区结构元数据、把用户输入的包名规范化为完全限定的包 ID、校验清单可解析，并在需要时读取合并后的配置值；给出把这些命令串成工具链的典型组合。

## 前提

- 工具在任意目录被调用时都应工作：用户可能从子目录触发命令，因此第一步总是定位清单。
- 这些命令输出到标准输出、供程序消费，退出码语义见[退出代码](../reference/exit-codes.md)；`<spec>` 表示包 ID 规范。
- `cargo config get` 属于不稳定门控命令（见第 5 步），工具集成前先确认运行环境。

## 步骤

### 1. 定位清单

```sh
cargo locate-project
cargo locate-project --workspace
cargo locate-project --message-format plain
```

[cargo locate-project](cli:command:locate-project) 从当前工作目录向上搜索最近的 `Cargo.toml`：默认输出当前包（工作区成员）的清单路径，`--workspace` 改为输出工作区根清单（必要时读取成员的 `package.workspace` 字段）。输出格式 `json`（默认）为 `{"root":"<绝对路径>"}`，`plain` 只打印路径。这是任何"从编辑器会话进入 cargo 世界"的工具的第一跳：

```json
{"root":"/path/to/my-package/Cargo.toml"}
```

### 2. 读取工作区元数据

```sh
cargo metadata --format-version 1
cargo metadata --no-deps --format-version 1
```

[cargo metadata](cli:command:metadata) 把工作区成员与解析后的依赖输出为一个 JSON 对象。消费约定：

- 始终显式传 `--format-version`（本版唯一取值 `1`），省略时 cargo 打印警告并按版本 `1` 输出（`metadata.rs`）；同一格式版本内向 JSON 追加新字段、新增枚举值不算破坏性变更，消费端必须容忍未知字段，`packages[].id` 这类"不透明标识"不应依赖其内部结构。
- 顶层字段包括 `packages`、`workspace_members`、`resolve`、`target_directory`、`workspace_root`、`version`、`metadata`（书《cargo metadata》的 JSON 格式）。
- `--no-deps` 只输出工作区成员且不解析、不拉取依赖，速度快且通常就是 IDE 需要的范围；`resolve` 字段此时为 `null`。
- `--filter-platform <TRIPLE>` 让 `resolve` 只含该目标的依赖；`packages` 数组始终是清单的完整再现。
- Rust 工具可用 cargo_metadata crate 解析（书推荐）；JSON 消息（构建诊断流）见工作流 04。

### 3. 规范化包 ID

```sh
cargo pkgid
cargo pkgid foo
cargo pkgid foo@1.0.0
```

[cargo pkgid](cli:command:pkgid) 把简写的 `<spec>` 解析为完全限定的包 ID 并打印（如 `foo` 得到 `registry+https://github.com/rust-lang/crates.io-index#foo@1.0.0` 一类）。SPEC 允许的写法（书《Package ID Specifications》）：`name`、`name@version`、URL 形式（`<url>#<name>`、`<url>#<name>@<version>` 等）；简写只要在依赖图中唯一即可，无法唯一指认时报错。pkgid 需要锁文件存在且依赖已拉取；完全限定的输出可直接作为 `-p`/`--package` 参数与 metadata、JSON 消息中对同一包的引用。

### 4. 校验清单

```sh
cargo verify-project
```

[cargo verify-project](cli:command:verify-project) 是隐藏的已弃用命令，用于快速判断当前目录能否构成合法的 cargo 项目：清单可解析时输出 `{"success":"true"}`；失败时输出 `{"invalid":"<错误信息>"}` 并以退出码 `1` 结束（`verify_project.rs`）。新工具不应把它当作长期接口，列入此处是为了读懂既有集成（如编辑器插件的旧探测逻辑）；它的存在与弃用都记录在本版本的来源说明中。

### 5. 读取配置值

```sh
# 说明性示例：需要 nightly 且显式开启 unstable-options
cargo +nightly -Zunstable-options config get build.target-dir
cargo +nightly -Zunstable-options config get registry --format json --show-origin
```

[cargo config get](cli:command:config/get) 打印合并后的配置：不带 KEY 时输出整棵配置树，带 KEY 时输出该键的值；`--format` 选 `toml`（默认）、`json`、`json-value`；`--show-origin` 标注每个值来自哪个配置层；`--merged no` 查看原始分层定义。注意：`config` 命令族受 `-Z unstable-options` 门控（feature 9301），在 stable cargo 上会直接拒绝执行——工具集成只能把它当可选增强，读取配置的稳定途径仍是 `--config` 命令行覆盖与各命令自身的配置键。

### 6. 组合成一次工具链调用

```sh
# 说明性示例：IDE 启动时的典型序列
root="$(cargo locate-project --message-format plain)"
cargo metadata --no-deps --format-version 1
cargo pkgid my-crate
```

典型接线：`locate-project` 决定工作目录锚点 → `metadata --no-deps` 拿包与目标结构 → 用户选中某个包时用 `pkgid` 换取稳定 ID，再用于 `cargo check -p <spec>` 之类的 `--message-format json` 调用。全部命令只读，不修改项目状态，可随时重复调用；注意它们都会触发清单解析，频繁调用时应在工具内缓存结果。

**风险与边界：** metadata 的 JSON 结构按"新增不算破坏"演进，硬编码字段列表的工具会随 cargo 升级而碎；不透明标识（`id`、来源 URL 内部形态）不要做字符串拼装，需要规范化就用 pkgid。`locate-project` 对非法清单的容错行为上游未说明，工具应把"找不到清单"视为正常分支。`verify-project` 已弃用、`config get` 不稳定，两者的存在都不构成稳定承诺，集成前准备降级路径。
