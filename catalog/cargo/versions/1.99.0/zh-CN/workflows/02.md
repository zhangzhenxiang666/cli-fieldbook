**适用场景：** 维护一个包的依赖集合：从注册表、git 仓库或本地路径添加依赖并施加 SemVer 约束，理解 `Cargo.toml` 与 `Cargo.lock` 各自记录什么，按需整体或定点升级，移除依赖时保持两份文件同步，并用依赖树检视实际解析结果，最后确定 Cargo.lock 的提交策略。

## 前提

- 项目已存在（见[新建并运行项目](01.md)），工作目录在包或工作区内；`<crate>` 表示 crate 名，`<spec>` 表示包 ID 规范（见工作流 08 的 SPEC 语法）。
- 依赖语义（SemVer、版本要求、来源种类）见[依赖](../concepts/dependencies.md)。
- 访问注册表依赖需要网络；离线场景见工作流 06。

## 步骤

### 1. 从注册表添加依赖

```sh
cargo add serde
# 说明性示例：指定版本要求、只开部分特性、加入开发依赖
cargo add nom@5
cargo add serde serde_json -F serde/derive
cargo add --dev trybuild
```

[cargo add](cli:command:add) 把依赖写入 `Cargo.toml` 的 `[dependencies]`（`--dev` 写入开发依赖、`--build` 写入构建依赖，`--target <TARGET>` 写入平台特定表）。版本写法：

- `cargo add serde` 不带版本时，add 查询注册表取最新兼容版本，并把该版本号写入清单（说明性示例：`serde = "1.0.219"`，具体数字以注册表为准）。
- `serde@5` 的 `@` 之后是完整 SemVer 版本要求，原样写入清单；裸版本号按插入符（`^`）语义解释，即 `5` 等价于 `^5`（书《Specifying Dependencies》的约定）。
- 已存在的依赖被再次 add 时按新给定的旗标更新原条目，不会重复。
- `-n`/`--dry-run` 只解析并显示将要写入的内容，不修改清单；成功时输出会列出该依赖启用（`+`）与未启用（`-`）的特性。

### 2. 从 git 或本地路径添加

```sh
# 说明性示例：git 来源固定到 rev；本地路径来源
cargo add --git https://github.com/rust-lang/regex regex --rev 9f9f693
cargo add --path ../utils my-utils
```

- git 来源用 `--git <URI>`，默认取默认分支最新提交，`--branch`/`--tag`/`--rev` 三选一固定引用；写入清单的是 `git` 表。
- 路径来源用 `--path <PATH>`，普通依赖会同时写入该包的版本号；开发依赖按约定可省略版本。工作区成员可被识别为路径依赖。
- 精确提交由 `Cargo.lock` 记录（见第 4 步），清单中无需手写 SHA。

### 3. 定点升级与重建锁文件

```sh
cargo update
cargo update regex
cargo update regex --precise 1.2.3
# 说明性示例：干跑，不写 Cargo.lock
cargo update -n
```

[cargo update](cli:command:update) 把 `Cargo.lock` 中的版本推进到满足清单要求的最新版：不带参数更新全部；给出一个或多个 `<spec>` 只更新指定包；`--precise <VERSION>` 与包选择参数同用，把该包固定到精确版本（与 `--recursive` 互斥）。`-w`/`--workspace` 只允许更新工作区成员包。`Cargo.lock` 不存在或被删除时，用 [cargo generate-lockfile](cli:command:generate-lockfile) 依据清单重新生成一份最新解析；update 在锁文件缺失时也会先创建。

### 4. 理解两份文件的变化边界

- `Cargo.toml` 是你书写的内容：宽泛的版本要求与来源；`Cargo.lock` 由 cargo 维护，记录最终选定的精确版本（含 git 提交），不应手改（书《Cargo.toml vs Cargo.lock》）。
- add 与 remove 同时改两份文件；update 与 generate-lockfile 只改 `Cargo.lock`；`--locked` 断言构建过程中锁文件不变。
- 提交策略：书的建议是拿不准时把 `Cargo.lock` 纳入版本控制；二进制项目应当提交以保证可复现构建，库项目也可提交。

### 5. 移除依赖

```sh
cargo remove regex
# 说明性示例：从开发依赖与平台特定表移除
cargo remove --dev trybuild
cargo remove --target wasm32-unknown-unknown nom
```

[cargo remove](cli:command:remove)（别名 `rm`）从对应表中删除条目并同步 `Cargo.lock`；`--dev`、`--build`、`--target` 决定从哪个表移除，`-n` 干跑。

### 6. 检视依赖图

```sh
cargo tree
# 说明性示例：查谁依赖 syn、看重复版本、解释特性来源
cargo tree -i syn
cargo tree -d
cargo tree -e features -i syn
```

[cargo tree](cli:command:tree) 打印解析后的依赖树。默认包含 normal、build、dev 三类边；`(*)` 表示重复包已去重（`--no-dedupe` 展示）；`-i <spec>` 反向显示依赖者；`-d` 只看因 SemVer 不兼容而并存的多版本；`-e <KINDS>` 选择边类型，`features` 配合 `-i` 可以解释某特性为何被启用。树展示的是接近统一解析的结果，与 `Cargo.toml` 中逐条声明不一定一一对应。

**状态变化一览：**

| 命令 | Cargo.toml | Cargo.lock |
| --- | --- | --- |
| `cargo add` | 写入/更新依赖条目 | 同步重解析 |
| `cargo remove` | 删除条目 | 同步重解析 |
| `cargo update` | 不修改 | 更新精确版本 |
| `cargo generate-lockfile` | 只读 | 缺失时重建、存在时重解析 |
| `cargo tree` | 只读 | 只读 |

**风险与边界：** `--precise` 指定的版本必须满足清单中的版本要求，否则解析失败且不写入。`cargo update` 整体更新可能拉入破坏性变更，先在版本控制中保持干净工作区再更新，便于回退。git 依赖的默认分支会随上游移动，只有 `Cargo.lock` 固定的提交是可复现的。`--dry-run` 各命令覆盖的阶段不同：add/remove 不写清单，update 不写锁文件，均已完成网络解析。
