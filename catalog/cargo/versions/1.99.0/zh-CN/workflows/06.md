**适用场景：** 让构建摆脱对网络的依赖：把全部注册表与 git 依赖的源码固化到仓库内的 vendor 目录并用来源替换接入（内网、审计、长期可复现），或仅按 `Cargo.lock` 预取依赖后以 `--offline` 构建（构建机断网、加速冷启动）。

## 前提

- 项目已有 `Cargo.toml`；`Cargo.lock` 已提交或愿意在预取时生成。
- vendored 流程会新增一个通常很大的 `vendor/` 目录，先确认版本控制与仓库体积约束；来源替换的机制见[配置](../concepts/configuration.md)。
- 本页给出的 `.cargo/config.toml` 内容为说明性示例，实际以 `cargo vendor` 自身打印的配置为准。

## 步骤

### 1. 生成 vendor 目录

```sh
cargo vendor > vendor-config.toml
# 说明性示例：指定目录、保留过期内容、附带同步其他工作区
cargo vendor third-party/vendor
cargo vendor --no-delete --versioned-dirs
cargo vendor -s ../other/Cargo.toml
```

[cargo vendor](cli:command:vendor) 把当前工作区（以及 `-s`/`--sync` 额外指定的清单）的全部远程依赖源码展开到指定目录（默认 `vendor`），并在标准输出打印启用它所需的 `.cargo/config.toml` 配置——这正是上面重定向到 `vendor-config.toml` 的内容。要点：

- `--no-delete` 保留目录中不再需要的 crate（用于手工维护的补丁）；`--versioned-dirs` 让同名多版本的目录名始终带版本号。
- vendor 本身仍需要网络；完成信号是退出码 `0` 与打印出的配置块。项目没有可 vendor 的远程依赖时，命令提示 `There is no dependency to vendor in this project.`（依据 `vendor.rs`）。
- 路径依赖与工作区成员不进入 vendor 目录，它们本来就以源码形式存在于仓库中。

### 2. 接入来源替换

```sh
mkdir -p .cargo && cat vendor-config.toml >> .cargo/config.toml
```

打印出的配置形如（说明性示例，以实际输出为准）：

```toml
[source.crates-io]
replace-with = "vendored-sources"

[source.vendored-sources]
directory = "vendor"
```

含义：把 crates.io 来源替换为指向本地 `vendor` 目录的目录来源（书《Source Replacement》）。git 依赖会各自得到一个单独的 `[source]` 表。配置写入项目的 `.cargo/config.toml`（man 手册的建议位置），也可以放到 `$CARGO_HOME/config.toml` 对全部项目生效。此后构建不再访问网络上的注册表。要临时回到在线模式，注释掉 `replace-with` 行即可；cargo 视 vendored 源为只读，改里面的代码请用 `[patch]` 或路径依赖指向一份可写副本。

### 3. 按锁文件预取

```sh
cargo fetch --locked
```

[cargo fetch](cli:command:fetch) 确保 `Cargo.lock` 中全部 git 与注册表依赖已下载到本地缓存（`$CARGO_HOME` 下的 registry/git 目录，见[环境变量](../reference/environment.md)）；锁文件缺失时先生成再下载。`--locked` 断言锁文件不变，避免预取与提交的版本漂移；`--target <TRIPLE>` 只取指定目标的依赖，不给则取全部目标。完成信号：退出码 `0`；fetch 后只要锁文件不变，后续命令都能离线运行。

### 4. 离线构建

```sh
cargo build --offline
```

`--offline` 禁止网络访问：所有需要的源已在缓存或 vendor 目录中则正常构建；缺任何东西都直接报错，而不是尝试联网。要点：

- [cargo build](cli:command:build) 之外，test、check 等同样接受该全局选项；`--frozen` 等价于 `--locked --offline`，适合完全封闭的环境。
- 完成信号与普通构建一致：`Finished` 行与退出码 `0`（见[退出代码](../reference/exit-codes.md)）。
- 验收建议：接入来源替换后先在线执行一次完整构建，确认 vendor 目录覆盖了包括 git 依赖与平台特定依赖在内的全部来源，再断网用 `--offline` 复验同一构建。

**适用边界：**

- vendored 方案适合内网、供应链审计与"多年后仍要能构建"的场景，代价是仓库体积与依赖升级时重新 vendor 的维护成本。
- fetch + `--offline` 适合构建机偶尔断网或要在离线窗口内批量执行命令的场景，不改变仓库内容。
- 两者都要求 `Cargo.lock` 可靠提交——没有锁文件，离线解析无从谈起。

**状态变化一览：**

| 命令 | vendor 目录 | `.cargo/config.toml` | 依赖缓存 |
| --- | --- | --- | --- |
| `cargo vendor` | 写入全部远程依赖源码 | 不修改（打印建议配置） | 写入 |
| 手工接入配置 | 只读 | 追加 `[source]` 表 | 只读 |
| `cargo fetch --locked` | 不涉及 | 只读 | 写入 |
| `cargo build --offline` | 只读 | 只读 | 只读 |

**风险与边界：** vendor 目录必须与 `Cargo.lock` 同步演进：清单变化后要重新运行 `cargo vendor` 并提交增删的目录，否则离线构建在缺包处失败。来源替换要求替换源与原来源内容一致，不能借它注入私有补丁（那属于 `[patch]` 的职责）。fetch 之后的缓存属于本机 `$CARGO_HOME`，不可复制给他人当作分发手段。vendored 构建下，需要直接联系注册表的命令（如 publish）必须显式给 `--registry` 消除歧义。
