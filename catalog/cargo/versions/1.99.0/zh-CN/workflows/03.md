**适用场景：** 在开发循环中驾驭 `cargo test` 的过滤与容错选项、用 `cargo bench` 跑基准、用 `cargo fix` 自动套用编译器建议（尤其是 edition 迁移），并读取 future-incompat 报告提前发现将来会被拒绝的依赖代码；统一以退出码判定结果。

## 前提

- 项目已有测试目标（`#[test]` 函数、`tests/` 集成测试或 `#[bench]` 目标）；工作目录在包或工作区内。
- `cargo fix` 会改写源码，要求版本控制可用且工作区干净（详见第 4 步）；`#[bench]` 属性与 `#[test]` 的微基准用法依赖 nightly 的 libtest 未稳定特性。
- `<TESTNAME>`、`<benchname>` 表示过滤串，`--` 之后的参数属于测试框架（libtest）而非 cargo。

## 步骤

### 1. 按名过滤测试

```sh
cargo test
# 说明性示例：子串过滤；在单个集成测试内精确匹配一个用例；传 libtest 参数
cargo test name_filter
cargo test --test int_test_name -- modname::test_name
cargo test foo -- --test-threads 3
```

[cargo test](cli:command:test) 的第一个位置参数 `TESTNAME` 与 `--` 之后的参数都原样传给测试二进制（libtest）：`TESTNAME` 按子串过滤测试名，`--exact` 要求全名精确匹配（基准示例：`cargo bench -- foo --exact`），`--test-threads` 控制并行度。默认编译并运行单元、集成与文档测试并顺带编译 examples；`--doc` 只运行文档测试；`--lib`、`--test <NAME>`、`--bin <NAME>` 等可缩小目标集合。`--no-run` 只编译测试不执行，用于 CI 预热或仅验证测试可编译。

### 2. 全量收集失败

```sh
cargo test --workspace --no-fail-fast
```

`--workspace`（别名 `--all`）覆盖工作区全部成员；默认任一测试目标失败即停止后续目标，`--no-fail-fast` 改为全部跑完后汇总。每个测试目标（单元、各集成测试、文档测试各算一个）输出一段自己的运行记录与汇总行，全部通过时各汇总行形如（书《Tests》快照的形态）：

```console
test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
```

判定：全部通过退出码为 `0`；失败时失败目标的退出码成为 cargo 的退出码（见[退出代码](../reference/exit-codes.md)），`--no-fail-fast` 下只要有失败最终仍非零。测试目标串行执行，工作目录为所属包根目录。

### 3. 运行基准

```sh
cargo bench
# 说明性示例：只跑一个基准目标里的一个基准
cargo bench --bench bench_name -- modname::some_benchmark
```

[cargo bench](cli:command:bench) 的过滤与参数传递和 test 相同。差异：默认使用 `bench` profile（开优化、去调试信息），需要调试时可 `--profile=dev`；基准的工作目录同样是包根目录。libtest 传给基准二进制 `--bench` 旗标使其只跑基准；目标清单里 `harness = false` 可换自定义入口。注意 `#[bench]` 属性本身在 stable 不可用（man 手册注明为 nightly 专属），stable 项目通常改用第三方基准 crate；`cargo test` 会以一次迭代试运行 `#[bench]` 函数，仅验证可执行。profile 的设定见[特性与 profile](../concepts/features-profiles.md)。

### 4. 自动修复与 edition 迁移

```sh
cargo fix
# 说明性示例：为迁移到下一个 edition 做准备；只修部分目标
cargo fix --edition
cargo fix --lib
```

[cargo fix](cli:command:fix) 在内部执行 [cargo check](cli:command:check)（`cargo fix` 等价于 `cargo check --all-targets`），把可机械套用的警告建议写回源码。要点：

- 安全阀：无版本控制时拒绝运行（`--allow-no-vcs` 放行）；git 工作区有未提交改动时拒绝（`--allow-dirty`、`--allow-staged` 放行，或先提交）。
- edition 迁移三步（man 手册）：`cargo fix --edition` 准备代码（必要时配 `--all-features`、多次 `--target` 覆盖条件编译代码）；手工把 `Cargo.toml` 的 `edition` 改为新值；再跑测试验证，残留警告可再跑一次不带 `--edition` 的 `cargo fix`。
- fix 只能修复当前被编译到的代码：可选特性需 `--features`，平台相关代码需 `--target`；个别情况编译器无法自动完成迁移，需手工收尾。

### 5. 读取 future-incompat 报告

```sh
# 说明性示例：构建时顺带打印完整报告；事后按 id 查看落盘报告
cargo check --future-incompat-report
cargo report future-incompatibilities --id 1
cargo report future-incompatibilities --package my-dep@0.0.1
```

构建、check、test 结束时若发现依赖中存在"未来会变成硬错误"的警告，会打印一段提示，指引用 `--future-incompat-report` 重跑或用 [cargo report future-incompatibilities](cli:command:report/future-incompatibilities)（别名 `future-incompat`）按 `--id` 查看上一次保存的报告；不带 `--id` 时显示最近一份，`--package` 只看某个包。处置方式是升级依赖到已修复版本或推动上游修复；报告频率可由 `[future-incompat-report] frequency` 配置（`always`/`never`）。

**状态变化一览：**

| 命令 | 源码 | target 目录 |
| --- | --- | --- |
| `cargo test` / `cargo bench` | 只读 | `debug/deps/` 下测试与基准可执行文件（bench 按 profile 输出） |
| `cargo fix` / `cargo fix --edition` | 写回 rustc 建议 | 与 check 相同的元数据 |
| `cargo report future-incompatibilities` | 只读 | 只读 |

**风险与边界：** `--no-fail-fast` 只影响是否继续执行，不改变"有失败即非零退出"的结论，脚本判断应只看退出码与汇总行。fix 改写源码前应确保改动已提交，避免与自动修复混在同一个 diff；`--edition` 只准备代码，改清单中的 edition 字段始终是手工步骤。bench 结果受机器负载影响，跨机器对比无意义。future-incompat 报告针对依赖代码，"当下仍能编译"与"未来仍能编译"是两回事。
