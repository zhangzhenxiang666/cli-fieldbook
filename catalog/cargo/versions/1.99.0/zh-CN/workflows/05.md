**适用场景：** 把一个包发布到 crates.io 或私有注册表：登录保存令牌、干跑打包核对内容、演练与正式发布、把协作者加为所有者，以及在版本有问题时收回（yank）；明确每一步的完成信号与失败后的恢复路径。

## 前提

- 包的元数据（`name`、`version`、`description`、`license` 等）已按发布要求填写；发布语义见[注册表与发布](../concepts/registries-publishing.md)。
- 需要一个注册表账号；crates.io 的 API 令牌从 `https://crates.io/me` 获取，令牌等同账号凭据，不要提交进仓库。
- 工作目录在待发布包内；`<crate>@<version>` 表示带版本的 crate 标识，`<user>` 表示对方用户名。

## 步骤

### 1. 登录保存令牌

```sh
cargo login
# 说明性示例：从标准输入读入令牌；登录到其他注册表
cat mytoken.txt | cargo login
cargo login --registry my-registry
```

[cargo login](cli:command:login) 把令牌交给凭据提供者保存：标准输入不是终端时（管道、重定向）从标准输入读入一行令牌；交互终端下则由凭据提供者自行提示输入（`login.rs` 的分支判断）。要点：

- 默认的 `cargo:token` 提供者把令牌明文写入 `$CARGO_HOME/credentials.toml`；推荐在 `$CARGO_HOME/config.toml` 配置 `registry.global-credential-providers`，用系统凭据管理（如 `cargo:macos-keychain`）优先、`cargo:token` 兜底（书《Registry Authentication》）。
- 位置参数直接给令牌的旧用法已弃用，会警告并要求改用标准输入；`--registry` 面向私有注册表。
- 完成信号：命令无报错退出；正确性由下一步的干跑验证。

### 2. 打包预检

```sh
cargo package --list
```

[cargo package](cli:command:package) 生成可分发的 `.crate` 压缩包到 `target/package/`；`--list` 只列出将被打包的文件，不实际打包。打包过程（man 手册）：重写并规范化 `Cargo.toml`（移除 `[patch]`、`[replace]`、`[workspace]` 段），总是包含 `Cargo.lock`（`--exclude-lockfile` 可排除），附 `.cargo_vcs_info.json` 记录提交哈希与 dirty 标记，遵循版本控制的忽略规则与清单 `include`/`exclude` 字段，随后解包到临时目录从头构建验证（`--no-verify` 跳过）。完成信号：`Packaging` → `Packaged` → `Verifying` 各状态行依次出现且退出码为 `0`。git 工作区不干净时拒绝执行，确认无碍后加 `--allow-dirty`。

### 3. 干跑演练

```sh
cargo publish --dry-run
```

[cargo publish](cli:command:publish) 的 `-n`/`--dry-run` 执行发布流程中除上传外的全部步骤（校验、打包、验证构建），成功后在 `target/package/` 留下 `.crate` 文件供检查——文件内容与体积（crates.io 限制 10MB）都在这一步核对。若清单带有 `package.publish` 限制（只允许发布到指定注册表），此处即会报错。

### 4. 正式发布

```sh
cargo publish
```

完整流程：校验（含 `package.publish`）→ 打包与验证 → `Uploading` 上传 → 服务端再校验并写入注册表索引 → 客户端轮询等待索引可见。完成与恢复信号（依据 `registry/publish.rs`）：

- `Uploaded` 表示上传已被接受（请求完成），还不是发布完成；默认最多等待 60 秒让索引生效，随后输出 `Published` 才是任务完成信号。等待期间可 Ctrl-C 跳过，不影响已完成的传输。
- 等待超时只是索引延迟，不代表失败：稍后直接查询注册表确认即可，不要立刻重发——同一版本号重复发布会被注册表拒绝。
- 发布下一个版本时手工递增 `Cargo.toml` 的 `version` 再走第 2–4 步。

### 5. 所有者协作

```sh
cargo owner --list foo
cargo owner --add <user> foo
cargo owner --remove <user> foo
```

[cargo owner](cli:command:owner) 管理注册表上的 crate 所有者：`--list` 列出；`--add`/`--remove` 增删。crates.io 的所有者 ID 是 GitHub 用户名或团队（`github:org:team`）：用户名为具名所有者，有权发布、yank 并再管理所有者（包括邀请者本人）；团队为受限所有者，仅能发布与 yank。未给出 crate 名时取当前目录包名。

### 6. 收回问题版本

```sh
cargo yank foo@1.0.7
# 说明性示例：撤销一次 yank
cargo yank foo@1.0.7 --undo
```

[cargo yank](cli:command:yank) 把某版本从注册表索引中标记为 yanked（`--undo` 恢复）。语义（man 手册与书《Publishing》）：不删除任何代码，下载链接仍可用；已有 `Cargo.lock` 的项目不受影响，新的解析不再选中该版本。因此 yank 前应先发布一个 SemVer 兼容的修复版本，避免依赖区间被切断；它只用于意外发布、无意破坏等例外情形，泄露机密时第一步永远是立即吊销凭据。

**状态变化一览：**

| 命令 | 注册表 | 本地 |
| --- | --- | --- |
| `cargo login` | 只读 | `$CARGO_HOME/credentials.toml`（或系统凭据库） |
| `cargo package` | 只读 | `target/package/` 下 `.crate` |
| `cargo publish --dry-run` | 只读 | 同上，不上传 |
| `cargo publish` | 新增版本并入索引 | 同上 |
| `cargo owner --add/--remove` | 修改所有者列表 | 只读 |
| `cargo yank` | 索引中标记 yanked | 只读 |

**风险与边界：** 发布不可撤销且同名同版本无法覆盖，务必先 `--dry-run`。路径依赖没有版本键时不能发布（`dev-dependencies` 除外）。令牌一旦泄露应立即吊销，yank 阻止不了已缓存副本的传播。`--token` 选项已弃用，推荐 `cargo login` 与环境变量（`CARGO_REGISTRY_TOKEN` 等，见[环境变量](../reference/environment.md)）。
