**适用场景：** 面向维护者发布一次 release 的完整路径：创建（自动说明、草稿与预发布选项）、补传资产、核对内容、校验 attestation（证明）、事后修正与取回，以及误发后的清理。

## 前提

- 已安装 gh 2.102.0，并已完成 [gh auth login](cli:command:auth/login) 认证；在目标仓库的 Git 检出内运行，或用 `-R`/`--repo` 指定仓库。
- 下文以 `<tag>` 表示 release 的 git tag（如 `v1.2.3`），资产路径（如 `./dist/*.tgz`）按实际发布物替换。
- 创建失败且提示可能缺少 `workflow` scope 时，按提示执行 `gh auth refresh -h <主机名> -s workflow` 补授权限。

## 步骤

### 1. 创建 release

```sh
gh release create <tag> --generate-notes
gh release create <tag> --notes "bugfix release" --verify-tag
gh release create <tag> './dist/app-linux-amd64#Linux build' --draft --prerelease
```

[gh release create](cli:command:release/create)（别名 `new`）：同名 tag 尚不存在时自动从默认分支最新状态创建，`--target` 让自动建 tag 指向其他分支或完整 commit SHA，`--verify-tag` 在远端没有该 tag 时中止创建。`--generate-notes` 通过 GitHub Release Notes API 自动生成标题与说明（未显式给标题时标题也自动生成），`--notes` 的附加说明会前置于自动生成部分。`--draft` 保存为草稿（不能与 `--discussion-category` 同用），`--prerelease` 标记预发布，`--latest`／`--latest=false` 显式控制 "Latest" 标记（默认按日期与版本自动判断）。资产跟在 tag 后给出，支持 glob 模式，文件名后追加 `#` 起始文本定义显示 label。非交互模式必须给出 tag，否则报错；成功后输出新 release 的 URL。

带资产创建非草稿 release 时，命令分多次 API 调用编排：先以草稿创建、上传资产、再发布，任一步失败都会清理掉草稿；若该 tag 已存在已发布 release 会直接报错。

### 2. 补传资产

```sh
gh release upload <tag> ./dist/*.tgz
gh release upload <tag> app.zip --clobber
```

[gh release upload](cli:command:release/upload) 按给出的 tag 查找目标 release（含按待定 tag 查找草稿 release），以固定并发 5 上传。目标 release 已有同名资产时：不加 `--clobber` 报错并列出冲突资产名；加 `--clobber` 先删除既有同名资产再上传——上传中途失败时原资产已经丢失、无法找回，因此覆盖前先确认旧资产不再需要。

### 3. 核对内容

```sh
gh release view <tag>
gh release view <tag> --json tagName,name,isDraft,isPrerelease,assets
```

[gh release view](cli:command:release/view) 不带 tag 时显示最新的 release；按 tag 查找时也能命中以待定 tag 保存的草稿 release。终端下以富文本渲染：草稿或 prerelease 显示徽标，随后是渲染后的 Markdown 说明与资产表（Name、Digest、Size）。`--json` 导出结构化字段（含 `isDraft`、`isPrerelease`、`isImmutable` 等），`--web` 在浏览器打开。

### 4. 校验 attestation

```sh
gh release verify <tag>
gh release verify-asset <tag> ./dist/app-linux-amd64
```

[gh release verify](cli:command:release/verify) 校验 release 附带有效的密码学签名 attestation（证明）：先把 tag 解析为 git ref 的 SHA，再拉取并按 tag 过滤 attestation，找不到 attestation 或发现重复 attestation 都会报错；通过时打印 tag 解析结果与带资产表（Name、Digest）的成功信息。[gh release verify-asset](cli:command:release/verify-asset) 先计算本机文件的 SHA-256 摘要，再与 attestation 中的 subject 比对，确认该文件确实来自指定 release。两者都支持 `--format json`（配合 `--jq`/`--template`）。并非所有 release 都有 attestation，没有时命令直接报错。

### 5. 修正与取回

```sh
gh release edit <tag> --draft=false
gh release edit <tag> --notes-file release-notes.md --latest
gh release download <tag>
gh release download --pattern '*.deb'
```

[gh release edit](cli:command:release/edit) 至少给出一个选项，否则报错；`--draft`、`--prerelease`、`--latest` 是三态旗标，`--draft=false` 即把草稿 release 发布。`--notes` 与 `--notes-file` 同用时以 `--notes-file` 为准；`--tag` 把 release 改到新 tag（`--verify-tag` 仅在改名时执行校验）。[gh release download](cli:command:release/download) 不带 tag 时从最新 release 下载，且必须给出 `--pattern` 或 `--archive`（后者取 `zip` 或 `tar.gz`，与 `--pattern` 互斥）；默认写入当前目录（`--dir` 可改），同名文件默认报错，`--clobber` 覆盖或 `--skip-existing` 跳过。

### 6. 清理路径

```sh
gh release delete <tag>
gh release delete <tag> --yes --cleanup-tag
```

[gh release delete](cli:command:release/delete) 在交互终端下先请求确认，`--yes` 跳过；非交互运行不出现确认提示，等价于直接删除。默认只删 release 本身，对应的 git tag 仍保留在仓库中，命令会输出提醒。`--cleanup-tag` 在删除 release 之外把远端 tag 一并删除，并顺带删除本地同名 tag（用 `--repo` 覆盖仓库时不删本地 tag）。

**状态变化一览：**

| 命令 | git tag | release | 资产 | 本地文件 |
| --- | --- | --- | --- | --- |
| `gh release create` | 缺失时自动创建 | 创建（可草稿） | 随命令上传 | 不修改 |
| `gh release upload` | 不修改 | 不修改 | 新增；`--clobber` 先删后传 | 读取文件 |
| `gh release view`／`gh release verify` | 只读 | 只读 | 只读 | 不修改 |
| `gh release verify-asset` | 只读 | 只读 | 只读 | 读取被校验文件 |
| `gh release edit` | `--tag` 时改名 | 修改属性／发布草稿 | 不修改 | 不修改 |
| `gh release download` | 不修改 | 只读 | 读取 | 写入资产或归档 |
| `gh release delete` | 默认保留；`--cleanup-tag` 删远端与本地 | 删除 | 随 release 删除 | 可能删除本地同名 tag |

**风险与边界：** 仓库启用 release 不可变性（immutability）后，发布后的 release tag 与资产不能修改或删除，保护仅在最终发布后生效——草稿 release 及其 tag 仍可修改或删除。`gh release upload --clobber` 先删后传，失败即丢失原资产。`gh release delete` 默认保留 tag，之后用同一 tag 重建 release 可能受既有 tag 影响，需要彻底清理时用 `--cleanup-tag`。`gh release create --fail-on-no-commits` 在自上个 release 以来没有新提交时使创建失败（仓库尚无任何 release 时不受影响）。`gh release verify` 系列依赖 GitHub 的 release attestation 能力，无 attestation 的 release 直接报错，创建命令不会补造 attestation。
