**适用场景：** 面向需要盯 CI 的开发者：手动触发一次工作流、列出并跟踪运行、排查失败步骤、按需重跑或取消，并处理工作流停用/启用与 Actions 缓存清理等周边状态。

## 前提

- 已安装 gh 2.102.0，并已完成 [gh auth login](cli:command:auth/login) 认证；在目标仓库的 Git 检出内运行，或用 `-R`/`--repo`、`GH_REPO` 指定仓库。
- 下文 `<run-id>`、`<job-id>`、`<workflow>`、`<branch>`、`<cache-key>` 分别表示运行 ID、job ID、工作流选择器（ID、名称或文件名）、分支与缓存键。
- 2.102.0 的 `gh run` 组没有 `status` 子命令（源码只注册 list、view、rerun、download、watch、cancel、delete）；"看当前状态"的等价视角是 [gh run list](cli:command:run/list) 过滤，拉取请求维度的检查用 [gh pr checks](cli:command:pr/checks)。

## 步骤

### 1. 触发与列出运行

```sh
gh workflow run <workflow> --ref <branch> -f environment=staging
gh run list --limit 10
gh run list --workflow <workflow> --all
gh run list --status in_progress
```

[gh workflow run](cli:command:workflow/run) 通过创建 `workflow_dispatch` 事件触发运行：工作流文件必须声明 `on.workflow_dispatch` 触发器，且只有处于启用状态的工作流会被匹配；`--ref` 决定运行哪个版本的工作流文件（默认仓库默认分支），工作流输入用 `-f`/`--raw-field`、`-F`/`--field`（值以 `@` 开头时从文件读取）或 `--json` 从标准输入给出。创建的运行 URL 在可用时会输出，随后用 [gh run view](cli:command:run/view) 或 gh run list 确认。[gh run list](cli:command:run/list)（别名 `gh run ls`）默认列 20 条，可按 `--branch`、`--user`、`--event`、`--commit`、`--created`、`--status` 过滤；注意 `-w` 传工作流名称时不会匹配已停用的工作流，要连同停用的一起看到须再加 `-a`。

### 2. 查看运行与排查失败步骤

```sh
gh run view <run-id>
gh run view <run-id> --job <job-id>
gh run view <run-id> --log-failed
gh run view <run-id> --exit-status || gh run view <run-id> --log-failed
```

[gh run view](cli:command:run/view) 展示运行摘要：头部信息、job 列表（`--verbose` 展开步骤）、注解与产物。`--job` 缩小到单个 job；`--log` 与 `--log-failed` 分别查看完整日志与失败步骤日志（二者互斥，`--web` 也与 `--log` 互斥）；`--exit-status` 在运行失败时以退出码 1 结束，便于接脚本分支。日志只在运行（或 job）完成后可查看。两条平台限制：以 zip 为主的获取方式关联不上 job 与日志时，gh 会改为逐个 job 经 API 获取（更慢更耗资源），缺失的 job 日志超过 25 个时操作报错——此时用 `--job` 缩小范围；个别日志行无法关联到具体步骤时，步骤名在输出中显示为 `UNKNOWN STEP`。

### 3. 跟踪到完成

```sh
gh run watch <run-id> --exit-status
gh run watch <run-id> --compact --interval 10
```

[gh run watch](cli:command:run/watch) 持续刷新展示运行进度直到完成，刷新间隔默认 3 秒（`--interval` 调整），期间可 Ctrl+C 退出；`--compact` 只显示相关/失败的步骤。运行已经完成时直接输出其结论后退出。`--exit-status` 在结论不是 `success` 时返回非零退出码，适合写 `gh run watch <run-id> --exit-status && 发布` 这类后续动作。监视输出中的注解受 `checks:read` 权限限制，本命令不支持细粒度 PAT 认证。

### 4. 重跑

```sh
gh run rerun <run-id> --failed
gh run view <run-id> --json jobs --jq '.jobs[] | {name, databaseId}'
gh run rerun --job <job-id> --debug
```

[gh run rerun](cli:command:run/rerun) 默认重跑整个运行；`--failed` 只重跑失败的 job，`--job` 重跑指定 job——两者都会连同依赖的 job 一起重跑。注意 `--job` 接受的是 job 的 `databaseId`，不是浏览器 URL 中 `jobs/` 后的数字（用后者会得到 `404 NOT FOUND`）；`databaseId` 用第二条命令导出。`--debug` 以调试日志重跑。服务器以 403 拒绝时，会报错提示该运行或 job 无法重跑。

### 5. 取消与删除

```sh
gh run cancel <run-id>
gh run cancel <run-id> --force
gh run delete <run-id>
```

[gh run cancel](cli:command:run/cancel) 提交取消一次运行的请求（`--force` 改为强制取消）；对已完成的运行发起取消会被服务器拒绝（HTTP 409）。成功只表示"请求已接受"，运行是否真的停下以 GitHub Actions 的实际状态为准。[gh run delete](cli:command:run/delete) 删除一次运行的记录；省略 ID 时交互终端下从近期运行（最多列出 10 条）中选择，非交互环境必须给出 ID。

### 6. 触发面管理：查看、停用与启用工作流

```sh
gh workflow list --all
gh workflow view <workflow> --yaml
gh workflow disable <workflow>
gh workflow enable <workflow>
```

[gh workflow list](cli:command:workflow/list)（别名 `gh workflow ls`）默认获取 50 个并隐藏已停用的工作流，`--all` 一并列出（`state` 取 `active`、`disabled_manually`、`disabled_inactivity`）。[gh workflow view](cli:command:workflow/view) 默认展示摘要（含近期运行表），`--yaml` 查看工作流文件内容，`--ref` 指定文件版本所在的分支或标签（必须与 `--yaml` 同用）。[gh workflow disable](cli:command:workflow/disable) 停用后工作流不再运行、也不出现在默认列表（对应 `gh run list -w` 匹配不到停用工作流的行为）；[gh workflow enable](cli:command:workflow/enable) 恢复运行并回到列表。disable 只匹配启用状态的工作流、enable 只匹配停用状态的工作流，名称匹配不区分大小写。

### 7. 清理 Actions 缓存

```sh
gh cache list
gh cache delete <cache-key>
gh cache delete --all --ref refs/heads/<branch>
```

[gh cache delete](cli:command:cache/delete) 要求令牌具有 `repo` scope 授权。可按缓存 ID（数字）或缓存键删除：同一键与 ref 的组合可能对应多条缓存，命令会删除匹配的全部条目并汇总数量；`--all` 删除全部缓存，可与 `--ref` 连用只删特定 ref（`refs/heads/<branch>` 或 `refs/pull/<PR 编号>/merge`）的缓存。先用 [gh cache list](cli:command:cache/list) 查看 ID 与键。找不到匹配缓存时报错；`--all` 配合 `--succeed-on-no-caches` 时无缓存也以退出代码 0 结束。删除即时生效且没有确认步骤，执行前核对作用范围。

**状态变化一览：**

| 命令 | 运行 | job | 工作流 | 缓存 |
| --- | --- | --- | --- | --- |
| `gh workflow run` | 新建一次运行 | 由平台调度 | 不修改 | 不涉及 |
| `gh run list`／`gh run view`／`gh run watch` | 只读 | 只读 | 只读 | 只读 |
| `gh run rerun` | 产生新的尝试 | 重跑失败／指定 job（含依赖） | 不修改 | 不涉及 |
| `gh run cancel` | 提交取消请求 | 停止执行（以平台实际状态为准） | 不修改 | 不涉及 |
| `gh run delete` | 删除运行记录 | 随运行不可再查 | 不修改 | 不涉及 |
| `gh workflow disable`／`gh workflow enable` | 不修改 | 不修改 | state 切换 | 不涉及 |
| `gh cache delete` | 不涉及 | 不涉及 | 不涉及 | 删除匹配条目 |

**风险与边界：** `gh run cancel` 的"成功"只是请求被接受；`gh run delete` 删除运行记录后，`gh run view`、`gh run rerun` 等命令不再能访问该 ID。缺失超过 25 个 job 日志与 `UNKNOWN STEP` 是平台限制而非命令缺陷，官方提示的处理方式都是用 `--job` 缩小范围。`gh run rerun --job` 用错 ID 形态只会得到 404，不提示正确取法，重跑前先导出 `databaseId`。工作流停用是切触发面的动作：停用期间 `workflow_dispatch` 也无法触发。缓存删除没有确认步骤，`--all` 的作用范围覆盖整个仓库（或指定 ref），脚本里建议配 `--succeed-on-no-caches` 让幂等清理不误报。
