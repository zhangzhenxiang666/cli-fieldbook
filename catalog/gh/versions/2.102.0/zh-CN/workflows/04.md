**适用场景：** 以评审人身份处理一个拉取请求：把改动检出到本地实际运行、读差异与元信息、给出通过／请求修改／评论三类评审之一，最后视权限代为合并收尾。面向参与他人分支评审的开发者。

## 前提

- 已安装 gh 2.102.0 并完成认证；在目标仓库的本地克隆内运行，仓库已有默认仓库设置（多远端歧义见[工作流 02](02.md)）。
- 提交评审需要你对仓库有相应权限；`--request-changes` 的评审在某些分支保护配置下会阻塞合并，给出前确认这是意图行为。
- 下文 `<number>` 表示拉取请求编号；不带参数的 pr 命令默认作用于当前分支对应的拉取请求，也可改用 URL 或头部分支名。

## 步骤

### 1. 检出到本地

```sh
gh pr checkout <number>
```

[gh pr checkout](cli:command:pr/checkout) 以头部分支名新建本地分支并建立跟踪后检出；`--branch <name>` 改用自定义本地分支名。本地已存在同名分支时检出该分支并同步到最新，`--force` 把它重置为拉取请求的最新状态——重置会丢弃本地分支上的独有提交，确认无用后再用。跨仓库拉取请求（来自复刻）而本地没有对应远端时，命令自动补齐必要的远端与抓取。交互模式下不带参数会从最近 10 个拉取请求中选择；非交互模式必须给出参数。`--detach` 以分离 HEAD 检出，`--worktree <path>` 检出到独立 worktree，不想污染当前工作区时可用。

### 2. 读差异

```sh
gh pr diff --color=always | less -R
```

[gh pr diff](cli:command:pr/diff) 输出拉取请求差异，`--color` 取值 `always`、`never`、`auto`（默认 `auto`，按输出目标决定是否着色），管道给分页器时用 `always` 保留颜色。默认输出会中和差异中的终端转义序列以防其操控终端；把补丁原样管道给其它程序（如 `git apply`）时加 `--allow-escape-sequences`。大变更先用 `--name-only` 看文件清单，`--exclude '<glob>'` 排除生成文件等噪声（可重复给出，模式一律用正斜杠）。`--web` 打开浏览器到 Files changed 页。

### 3. 提取元信息

```sh
gh pr view <number> --json number,title,author,baseRefName,headRefName,additions,deletions,changedFiles,commits,reviewDecision,statusCheckRollup,mergeable,mergeStateStatus,url
```

[gh pr view](cli:command:pr/view) 默认渲染人类可读的预览；`--json` 按白名单字段输出结构化数据，配合 `--jq` 直接过滤，例如只要标题与作者：

```sh
gh pr view <number> --json title,author --jq '"\(.author.login): \(.title)"'
```

`statusCheckRollup` 与 `mergeStateStatus` 可在本地运行测试前先判断 CI 与可合并性，`mergeStateStatus` 还能提示分支是否落后。要看评论用 `--comments`，它与 `--json` 互斥；`--web` 打开浏览器查看。

### 4. 本地运行验证

在检出的分支上执行构建与测试（普通的构建命令，不属于 gh 的职责范围）。这一步只消费第 1 步建立的本地分支；评审过程中作者推送了新提交时，再次运行 `gh pr checkout <number> --force` 可把本地分支重置到最新状态（丢弃本地未推送的改动），再重新验证。

### 5. 提交评审

```sh
gh pr review <number> --comment --body "整体思路没问题，补充一个测试角度"
gh pr review <number> --request-changes --body "错误处理分支会 panic，请修复后再提交评审"
gh pr review <number> --approve
```

[gh pr review](cli:command:pr/review) 以三种类型之一提交评审：`--approve`（通过）、`--request-changes`（请求修改）、`--comment`（仅评论）。约束来自源码校验：三个类型旗标必须恰好给一个；`--request-changes` 与 `--comment` 要求正文非空（`--body` 或 `--body-file`），`--approve` 的正文可省；只给 `--body` 不给类型旗标会报错。

评审正文是整条评审的 Markdown 文本。需要逐行给出建议时，gh 2.102.0 没有提供按行评论或建议块的旗标（命令仅注册上述类型旗标与 `--body`/`--body-file`），行内建议需改在网页评审界面完成；终端侧可把行号写进 `--body` 的正文里说明。

### 6. 合并收尾

```sh
gh pr merge <number> --squash --delete-branch
```

评审通过且检查全绿后，有合并权限的评审人可用 [gh pr merge](cli:command:pr/merge) 收尾。策略三选一（`--merge`／`--squash`／`--rebase`，非交互必须显式给出），`--auto` 在要求满足后自动合并，适合检查尚未跑完时先表态；`--delete-branch` 合并后删除远端与本地头部分支并切回基分支。已合并的拉取请求仍可用 `gh pr checkout <number>` 检出，命令正常返回。检查与合并队列的行为细节见[工作流 03](03.md)。

**状态变化一览：**

| 命令 | 本地 git | 远端拉取请求 |
| --- | --- | --- |
| `gh pr checkout` | 新建或切换本地分支并跟踪；跨仓库时补远端 | 只读 |
| `gh pr diff`／`gh pr view` | 只读 | 只读 |
| `gh pr review` | 只读 | 新增一条评审（通过／请求修改／评论） |
| `gh pr merge` | `--delete-branch` 删除本地分支并切回基分支 | 合并；`--auto` 设置自动合并标志 |

**风险与边界：** `gh pr checkout --force` 会把既有本地分支重置为远端状态，本地未推送的提交可能丢失；评审中自己的笔记建议放在别的分支或 `git stash`。`gh pr diff` 默认中和转义序列是有意设计，用 `--allow-escape-sequences` 管道补丁给其它程序前应确认来源可信。`gh pr review` 的交互流程（不带类型旗标）依赖终端提示，脚本中必须显式给出类型旗标；评审能否阻塞合并、重复评审如何计状态，由服务端与分支保护规则决定，gh 侧只负责提交评审。
