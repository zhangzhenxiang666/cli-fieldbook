**适用场景：** 以作者身份走完一个拉取请求的全程：从功能分支创建拉取请求、跟踪 CI 检查、失败时取日志排查、分支过期时更新，最后按仓库允许的策略合并并清理分支。面向在自己或所属组织的仓库里提交改动的开发者。

## 前提

- 已安装 gh 2.102.0 并完成认证；本地仓库已通过 [`gh repo set-default`](cli:command:repo/set-default) 或克隆行为确定默认仓库（多远端时的目标歧义见[工作流 02](02.md)）。
- 仓库需已启用拉取请求；合并策略（merge、squash、rebase）由仓库设置决定可用范围。
- 下文 `<branch>` 表示功能分支，`<number>` 表示拉取请求编号；不带编号参数的 pr 命令默认作用于当前分支对应的拉取请求。

## 步骤

### 1. 从功能分支创建拉取请求

```sh
git switch -c <branch>
# …提交改动…
gh pr create --fill
```

[gh pr create](cli:command:pr/create) 默认以当前分支为头部分支、仓库默认分支为基分支（可用 `--base` 覆盖；也可用 `git config branch.<branch>.gh-merge-base <base>` 为分支固定基分支）。`--fill` 从提交信息自动填充标题与正文，`--fill-first` 只取首个提交，`--fill-verbose` 额外带上提交正文，三者互斥；`--title`/`--body` 显式给出时优先于 `--fill` 的自动填充。

交互模式（未给 `--title` 与 `--body`）会依次提示标题与正文，正文提示前会列出仓库的拉取请求模板供选择，`--template <file>` 可指定；`--editor` 改为在编辑器中撰写（第一行标题、其余为正文），`--web` 改为在浏览器完成创建。

两个常见分支情形：

- 当前分支尚未推送到远端时，会提示选择推送位置，并提供建立复刻的选项（以这种方式创建的复刻只包含上游默认分支）；显式给出 `--head` 可跳过全部推送与复刻行为。
- 需要他人评审时，创建时用 `--reviewer <handle>` 请求（个人或团队），比事后补加省一步。

草稿用 `--draft` 标记，之后用 [`gh pr ready`](cli:command:pr/ready) 转正。

### 2. 状态看板：gh pr status

```sh
gh pr status
```

[gh pr status](cli:command:pr/status) 按三部分汇总：当前分支对应的拉取请求、自己创建的拉取请求、等待自己评审的拉取请求；每个条目带编号、标题、CI 检查与评审状态，`--conflict-status` 追加合并冲突状态。注意它始终以当前仓库与当前分支为上下文，不接受位置参数；用 `-R` 指定仓库时不显示"当前分支"部分。要看单项检查的细节转入下一步的 `gh pr checks`。

### 3. 等待 CI：gh pr checks --watch

```sh
gh pr checks --watch --fail-fast
```

[gh pr checks](cli:command:pr/checks) 列出拉取请求的检查项及状态。`--watch` 进入监视模式，默认每 10 秒刷新一次并提示 `Press Ctrl+C to quit`（`--interval` 调整秒数）；`--fail-fast` 在首个检查失败时立即退出监视，不必等其余检查结束。`--required` 只显示必需检查。

退出代码可用于脚本分支：有检查失败为 `1`；未用 `--watch` 时仍有待定检查为 `8`（`--watch` 会一直刷新到检查完成）。`--watch` 与 `--json` 互斥；`--json` 输出含 `bucket` 字段，把每项 `state` 归类为 `pass`、`fail`、`pending`、`skipping` 或 `cancel`。

### 4. 失败排查：定位运行并取失败日志

```sh
gh pr checks
gh run view <run-id> --log-failed
```

`gh pr checks` 输出中失败的检查项带有详情链接，`--json` 输出还包含所属 `workflow` 名称；在终端继续排查时，用 [gh run view](cli:command:run/view) 的 `--log-failed` 只取失败步骤的日志（日志仅在运行完成后可查看；运行失败时其摘要末尾也会提示这条命令）。用 `gh run view <run-id> --exit-status` 可让命令在运行失败时以非零退出码结束，便于把"是否通过"交给脚本判断；要看完整日志改用 `--log`，二者互斥。修复后在同一分支继续提交推送，拉取请求自动纳入新提交，回到第 3 步重新等检查。

### 5. 基分支前进后更新过期分支

```sh
gh pr update-branch
```

[gh pr update-branch](cli:command:pr/update-branch) 用基分支的最新提交更新拉取请求分支：默认以合并提交方式更新，`--rebase` 改为变基到基分支之上。更新在服务端完成，不改动本地分支。拉取请求分支与基分支存在冲突时报错退出且不做更新——此时需要先在本地解决冲突并推送；分支已不落后时提示无需更新。

### 6. 合并并清理分支

```sh
gh pr merge --squash --delete-branch
```

[gh pr merge](cli:command:pr/merge) 的三种策略至多给一个：`--merge` 并入基分支、`--squash` 压成一个提交并入、`--rebase` 变基并入。交互模式下未给策略会提示选择；非交互模式（如脚本）必须显式给出其一，否则报错。合并提交信息可用 `--subject`/`--body` 调整。

两个值得区分的机制：

- `--auto` 先为拉取请求启用自动合并，必需要求全部满足后才真正合并；`--disable-auto` 取消。目标分支启用了合并队列时无需指定策略：必需检查尚未通过会自动启用自动合并，已通过则直接加入合并队列，`--admin` 可绕过队列直接合并。合并队列中的拉取请求不能再用 `-d`/`--delete-branch`。
- `--delete-branch` 在合并后删除远端与本地头部分支；本地清理时若当前正处于头部分支，gh 会先检出（或新建跟踪）基分支并拉取，再删除本地分支，最后提示已切换到的分支。

**状态变化一览：**

| 命令 | 远端拉取请求 | 远端分支 | 本地 git |
| --- | --- | --- | --- |
| `gh pr create` | 创建（可标记草稿、请求评审） | 分支未推送时按确认推送或新建复刻 | 不修改既有提交 |
| `gh pr status`／`gh pr checks` | 只读 | 只读 | 只读 |
| `gh pr update-branch` | 头部分支被服务端更新（合并提交或变基） | 头部分支前进 | 不修改 |
| `gh pr merge` | 合并；`--auto` 设置自动合并标志 | `--delete-branch` 删除头部分支 | `--delete-branch` 删除本地分支并切回基分支 |

**风险与边界：** `gh pr create` 的 `--dry-run` 只打印详情但仍可能推送 git 变更，不要把它当作完全无副作用。`gh pr update-branch --rebase` 会改写远端头部分支的提交，协作者基于旧提交的本地分支需要重新对齐。`gh pr merge` 不带策略在脚本中会直接报错，不要依赖交互回退；`--admin` 绕过的是分支保护要求，仅在有管理员权限且确认必要时使用。合并队列与 `--delete-branch` 互斥：入队即交给队列接管，分支清理策略以仓库配置为准。
